# dotfiles-install

Intelligent installer for **this** dotfiles repo. A plain `bash install.sh` blindly backs up and symlinks; this skill first **inventories the existing state**, **proposes reconciliation (절충안)** for every conflict, then drives the install and verifies it. Use it whenever deploying this repo to a machine.

## Operating principles

- **Inventory before mutation.** Never overwrite or symlink until you've reported what's already there.
- **Reconcile, don't clobber.** When live config diverges from the repo, propose a merge and surface conflicts — preserve machine-specific additions instead of losing them.
- **Backups are mandatory.** Anything replaced gets a timestamped `.backup.<ts>` copy (this matches `install.sh`'s `link()`).
- **Idempotent.** Skip tools already installed and symlinks already correct.
- **Secrets are sacred.** `claude/secrets.env` is git-crypt encrypted. Never print its decrypted contents; never commit the master key.

## Critical precondition

`install.sh` **hardcodes** symlink sources as `~/.config/dotfiles/...`. The repo MUST be cloned to `~/.config/dotfiles`. First, confirm:

```bash
test "$(git -C . rev-parse --show-toplevel)" = "$HOME/.config/dotfiles" && echo OK || echo "WRONG LOCATION"
```

If wrong, stop and tell the user to clone/move the repo to `~/.config/dotfiles` (or the symlinks will dangle). Do not proceed.

## Phases

Run these in order. Report findings between phases; only ask the user when a decision is genuinely theirs (see `references/reconciliation.md`).

### Phase 0 — Inventory ("기존에 있던 값이 뭐가 있고")

Detect and report, as a table, the current state. Read `references/reconciliation.md` for the full checklist and the exact commands. At minimum:

1. **OS / distro** (`uname`, `/etc/os-release`) — drives package-manager choices.
2. **Already-installed tools** — `git-crypt`, `lsd`, `bat`, `nvim`, `tmux`, `starship`, `zinit`, `uv`, `lazygit`, `claude-notify`. Mark each ✓installed / ✗missing.
3. **Each symlink target** — for every row in the table below, classify as: missing / real file (will back up) / already-correct symlink / symlink-pointing-elsewhere.
4. **`~/.claude/settings.json` divergence** — compare live vs `claude/settings.json` key-by-key. This is the highest-value check (the live file is often edited in-app and drifts).
5. **git-crypt lock state** — is `claude/secrets.env` plaintext (unlocked) or `\0GITCRYPT` binary (locked)? `head -c 9 claude/secrets.env | grep -q GITCRYPT` → locked.
6. **Master key availability** — does `~/dotfiles-gitcrypt.key` exist for unlocking?

Symlinks this repo manages:

| Target | Source |
|---|---|
| `~/.config/nvim` | `dotfiles/nvim` |
| `~/.config/neofetch` | `dotfiles/neofetch` |
| `~/.claude/skills` | `dotfiles/claude/skills` |
| `~/.claude/CLAUDE.md` | `dotfiles/claude/CLAUDE.md` |
| `~/.zshrc` | `dotfiles/zsh/.zshrc` |
| `~/.config/starship.toml` | `dotfiles/terminal-tools/starship.toml` |

**`~/.claude/settings.json` is NOT symlinked — it is GENERATED** by
`claude/gen-claude-settings.py`: committed non-secret base (`claude/settings.json`)
**+** an `env` block injected from the decrypted `claude/secrets.env`. This makes
tokens "global Claude env vars" (apply to every session regardless of launch)
without committing them to the public repo. The output is a local, mode-600 file.

### Phase 1 — Reconcile ("절충안")

For each conflict found in Phase 0, apply the rule in `references/reconciliation.md`. Summary:

- **Real file where symlink expected** → back up (`mv x x.backup.<ts>`) then symlink. Safe default, no need to ask.
- **`settings.json` (generated, not symlinked)** → the live `~/.claude/settings.json` is regenerated by `gen-claude-settings.py`. Before regenerating, compare the live file's **non-secret keys** against the repo base (`claude/settings.json`); if the live file has drifted (e.g. plugins toggled in-app), offer to capture that drift back into the repo base so it isn't lost. **Never** copy the live `env` block (secrets) into the committed base. Then run the generator (it injects the `env` block from `secrets.env` itself).
- **secrets.env locked** → if `~/dotfiles-gitcrypt.key` exists, run `git-crypt unlock ~/dotfiles-gitcrypt.key`. If not, tell the user to bring the key (from their password manager) or fall back to `cp claude/secrets.env.example claude/secrets.env` for manual entry. Then run `gen-claude-settings.py` so the env block is injected. Never block the rest of the install on this — without the key the generator writes the base only.
- **Already correct** → report ✓ and skip.

### Phase 2 — Install components (sequential)

Drive the real installers. Prefer running the repo's own `install.sh` (it is idempotent, does backup-then-link for symlinks, and runs `gen-claude-settings.py` to generate `~/.claude/settings.json`). Run it **after** Phase 1 has captured any non-secret live drift into the repo base. The canonical order `install.sh` runs:

1. `install/node_setup.sh` — Node (for nvim Copilot etc.)
2. `terminal-tools/setting.bash` — lsd, bat, neofetch, lazygit, uv + aliases
3. `zsh/python_dev_install_script.sh` — pyenv, poetry, python tooling
4. `nvim/nvim_install.sh` — Neovim + vim-plug + plugins
5. `tmux/tmux_setup_script.sh` — tmux + TPM + plugins
6. `container-tools/install.sh`
7. `claude/install.sh` — Claudia GUI + claude-notify
8. tealdeer (tldr), 9. Zinit, 10. Starship, 11. git-crypt
12. symlinks (table above) + **generate** `~/.claude/settings.json` via `gen-claude-settings.py`
13. git-crypt unlock + re-generate reminder

You may run `bash install.sh` wholesale, or run components individually when only some are missing (use the Phase 0 inventory to skip satisfied ones). Stream progress; on any installer failure, stop and report the error rather than continuing silently.

### Phase 3 — Activate secrets

After installs and symlinks:

1. If still locked and the key is now available, `git-crypt unlock ~/dotfiles-gitcrypt.key`.
2. **Re-run `python3 ~/.config/dotfiles/claude/gen-claude-settings.py`** — now that secrets are unlocked, this injects the `env` block into `~/.claude/settings.json`, making the tokens global Claude env vars.
3. Confirm `~/.zshrc` (now symlinked) contains the guarded `source` block for `claude/secrets.env` (this covers terminal tools like `gh`/`git`).
4. Remind the user: the generated `env` block is read by Claude Code on launch (independent of shell), but a **running** Claude Code won't see it — **restart Claude Code**. Shell tools need a **new** terminal or `source ~/.zshrc`.

Note: `ANTHROPIC_API_KEY` in the env block overrides subscription auth and applies to terminal sessions only; the Claude Desktop chat app's MCP servers read their own config, not this. Generic tokens (e.g. `GITHUB_TOKEN`) work for the Claude Code process and the tools it spawns.

### Phase 4 — Verify

- Every managed symlink resolves to the correct repo source (`readlink`).
- `~/.claude/settings.json` is valid JSON, is a **real file (not a symlink), mode 600**, and contains the expected base keys. If secrets were unlocked, confirm an `env` block exists with the expected **key names** (verify keys, **never** print values).
- Installed tools resolve on `PATH`.
- If unlocked: `claude/secrets.env` is plaintext and sourcing it sets the expected vars (verify a var name exists, **never** print values).
- Report a final ✓/✗ checklist.

## Guardrails

- The repo is **public** (`github.com/DJ02-a/dotfiles`). Never write a real secret into any committed file other than the git-crypt-encrypted `claude/secrets.env`. Before any commit, run `git-crypt status -e` and confirm `secrets.env` shows `encrypted`.
- Do not commit or push unless the user explicitly asks.
- Symlinking `~/.claude/settings.json` may trip an auto-mode permission guard because it contains permission rules — if blocked, hand the exact `mv … && ln -s …` command to the user to run via `!` rather than forcing it.
